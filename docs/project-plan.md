## 1. 品牌与项目一句话定义

**品牌名：轻记**

**宣传语：记录更快，工作更轻。**

轻记是一款面向日常工作的 AI 快速记录工具，帮助用户快速记录任务、会议纪要、工作进展和用户需求，并通过 AI 优化、提炼和整理零散内容。

当前确认的核心方向：

1. 尽可能降低记录成本，让用户想到时可以立即记下来。
2. 使用 AI 快速优化文案并整理原始记录。
3. 将零散信息转化为清晰、可继续处理的工作内容。

> 待调整：本文后续章节仍主要描述个人任务管理场景，下一轮需要重构为“快速记录 + AI 整理 + 多种工作记录类型”的产品规划。

## 2. 项目目标

### 2.1 用户目标

- 降低记录成本：用户不用先整理分类，也能在数秒内创建任务。
- 降低决策成本：首页直接呈现今天最需要处理的内容。
- 降低遗忘风险：重要任务可以设置时间，并获得可靠提醒。
- 提供完成感：完成操作明确、轻松，并能看到当日进展。

### 2.2 产品目标

- 完成一个可独立使用的 MVP（最小可用版本，即功能不多，但核心流程完整）。
- 验证“快速记录 + 今日聚焦 + 轻提醒”是否足以形成持续使用。
- 建立可扩展的设计规范和代码结构，后续能加入重复任务、清单协作等功能，而不推翻第一版。

### 2.3 暂不设定的目标

- 暂不以商业化、用户增长或社交传播作为第一阶段目标。
- 暂不追求覆盖团队项目管理、知识库、日历等全部效率场景。
- 正式产品第一版聚焦 Mac 原生应用与桌面小组件；浏览器版仅用于快速验证交互与收集反馈，iPhone 版本后续复用核心代码跟进，Android 暂不规划。

## 3. 目标用户与场景

### 3.1 初始目标用户

工作与生活任务较多，但不愿维护复杂任务系统的个人用户。

典型特征：

- 经常临时想到待办事项。
- 会因为任务分散在聊天、备忘录和脑海中而焦虑。
- 使用过待办工具，但容易因录入步骤多或分类复杂而放弃。
- 更需要“现在做什么”的答案，而不是精细的项目管理报表。

### 3.2 核心使用场景

| 场景 | 用户行为 | 产品应提供的结果 |
| --- | --- | --- |
| 临时想到一件事 | 快速输入一句话 | 任务立即保存，稍后可再整理 |
| 开始一天 | 打开首页 | 看见今天、逾期和最重要的任务 |
| 安排重要事项 | 设置日期或时间 | 任务进入对应列表并按时提醒 |
| 完成任务 | 点击完成 | 即时反馈，任务从当前列表移出 |
| 计划变化 | 延后或取消 | 少量操作即可完成，不要求重新创建 |

## 4. 产品原则

后续遇到功能取舍时，按以下顺序判断：

1. **先记录，再整理**：创建任务不能被分类、标签等设置阻断。
2. **首页给答案**：首页优先回答“我现在要做什么”，不堆积数据。
3. **默认简单，高级能力渐进出现**：常用操作直接可见，低频设置按需展开。
4. **提醒有价值，不制造噪音**：只有用户明确设置的关键时间才主动打扰。
5. **操作可恢复**：完成、删除、延后等高频操作应提供撤销机会。
6. **视觉服务于行动**：优先保证层级、可读性和触达效率，不用装饰掩盖信息。

## 5. MVP 范围

### 5.1 必须包含

#### A. 快速创建任务

- 从首页直接输入任务标题。
- 创建时允许不设置日期、时间和分类。
- 可选设置日期、具体时间、优先级和备注。
- 保存后立即出现在正确列表中。

#### B. 今日首页

- 展示今天的任务。
- 单独提示逾期任务。
- 支持完成、取消完成和延后。
- 空状态给出下一步操作，而不是只显示空白页面。

#### C. 任务列表

- 今天。
- 计划内：未来有日期的任务。
- 收集箱：尚未安排日期的任务。
- 已完成。

#### D. 任务详情

- 编辑标题、备注、日期、时间和优先级。
- 删除任务前说明影响，删除后短时间内可撤销。
- 记录完成状态。

#### E. 提醒

- 有明确时间的任务可设置提醒。
- 首次使用提醒时再申请系统通知权限。
- 用户拒绝权限后，APP 内仍能正常使用，并提供清晰的重新开启入口。

#### F. 基础设置

- 通知设置入口。
- 浅色、深色或跟随系统（具体首版支持范围待确认）。
- 基础数据说明与隐私说明。

#### G. 桌面小组件

- 第一版支持将小组件添加到 Mac 桌面和通知中心。
- 在小组件中快速查看近期、置顶或待处理的工作记录。
- 支持通过按钮或开关直接执行完成、恢复、置顶等轻量操作。
- 点击新增或编辑入口时，直接打开对应记录的极简编辑界面。
- 小组件展示隐私内容时提供隐藏或脱敏策略。
- iPhone 主屏幕小组件在 Mac 版本验证后复用同一领域模型实现。

### 5.2 第一版不做

- 团队协作、任务指派和成员权限。
- 聊天、评论和动态流。
- 复杂项目、甘特图、看板和工时统计。
- AI 自动拆解任务或大模型聊天助手。
- 跨应用自动化和开放 API。
- 游戏化积分、排行榜和社交分享。
- 多层级子任务、复杂标签体系和自定义字段。

这些能力不是永久排除，而是在核心使用价值被验证前不投入。

## 6. 信息架构

建议第一版使用四个一级入口：

```text
任务省心记
├── 今日
│   ├── 逾期任务
│   ├── 今日任务
│   └── 快速创建
├── 计划
│   ├── 未来任务
│   └── 日期筛选
├── 收集箱
│   └── 未安排任务
└── 我的
    ├── 已完成
    ├── 通知设置
    ├── 外观设置
    └── 关于与隐私
```

任务详情通过列表进入，不占用一级入口。

## 7. 核心用户流程

### 7.1 快速记录

打开 APP → 点击输入区或新增按钮 → 输入任务 → 保存 → 任务进入“收集箱”或指定日期列表。

验收重点：用户从打开首页到保存一个无日期任务，不超过 3 个主要动作。

### 7.2 安排并提醒

打开任务 → 选择日期 → 可选具体时间和提醒 → 保存 → 到达时间后收到系统通知 → 点击通知进入任务详情。

验收重点：设置日期不强制设置时间；设置提醒时必须让用户知道何时会被通知。

### 7.3 完成任务

在列表点击完成 → 显示轻量完成反馈 → 任务从当前未完成列表移出 → 短时间展示“撤销”。

验收重点：反馈立即出现；误触后可以恢复。

### 7.4 延后任务

对任务执行延后 → 选择常用时间或自定义日期 → 任务移动到新日期 → 当前列表同步更新。

验收重点：常用选项建议包括“明天”和“下周”，具体选项在原型测试中确认。

## 8. 页面规划

| 页面 | 核心任务 | 关键内容 | 优先级 |
| --- | --- | --- | --- |
| 今日首页 | 判断今天做什么 | 逾期、今日任务、快速创建、完成反馈 | P0 |
| 新建任务 | 快速记录 | 标题、日期、时间、优先级、备注 | P0 |
| 任务详情 | 查看和修改任务 | 完整字段、完成、延后、删除 | P0 |
| 计划 | 查看未来安排 | 按日期分组的未来任务 | P0 |
| 收集箱 | 整理未安排事项 | 无日期任务、快速安排日期 | P0 |
| 已完成 | 回看已完成事项 | 完成时间、恢复任务 | P1 |
| 设置 | 管理通知和外观 | 权限状态、主题、隐私说明 | P1 |
| 首次引导 | 解释核心价值 | 最少步骤的价值说明与权限引导 | P1 |

优先级说明：P0 是首版闭环不可缺少；P1 是重要但可在核心流程稳定后补齐。

## 9. 交互与视觉规划

### 9.1 交互要求

- 高频操作单手可达，主要新增入口保持稳定。
- 列表项默认只展示判断任务所需的信息，备注等内容进入详情查看。
- 滑动手势只能作为快捷方式，同一操作必须有可发现的按钮入口。
- 删除等不可逆操作需要二次确认或可靠撤销。
- 加载、空状态、错误、无网络和权限被拒绝都要有明确反馈。
- 动效只解释状态变化，不能拖慢连续完成任务的操作。

### 9.2 首轮视觉方向

- 气质：轻松、清楚、可靠，避免企业项目管理工具的压迫感。
- 信息密度：中低密度，首页留出呼吸感，但不牺牲任务浏览效率。
- 色彩：中性色作为主体，只用一个品牌强调色表示主要行动。
- 状态不能只依赖颜色，还需结合图标、文字或形状，保证可访问性。
- 正文和关键操作满足移动端可读性与触控尺寸要求。

### 9.3 需要建立的设计规范

- 颜色、字体、间距、圆角、阴影等基础变量。
- 按钮、输入框、任务卡片、日期选择、弹窗、提示条等组件。
- 组件的默认、按下、禁用、错误、完成等状态。
- 空状态、加载状态、错误状态和权限状态模板。

### 9.4 浏览器交互原型

- 原型覆盖快速记录、记录类型、AI 整理、编辑、完成、列表筛选、Mac 小组件预览和体验反馈。
- 视觉与交互参考 Godly 的高对比编辑式排版、留白、圆角卡片和克制动效，不复制其品牌资产或具体页面。
- 原型数据保存在当前浏览器，用于验证流程，不作为正式产品的数据方案。
- 原型验证重点是用户能否理解“先记录、AI 再整理”，以及桌面小组件是否值得进入 Mac MVP。

## 10. 数据与技术规划

本节定义当前技术方向与能力边界；完整技术方案仍需在交互原型确认后形成。

### 10.1 核心数据对象

一个任务至少需要：

| 字段 | 用途 |
| --- | --- |
| `id` | 唯一识别任务 |
| `title` | 任务标题 |
| `note` | 可选备注 |
| `dueDate` | 可选日期 |
| `dueTime` | 可选具体时间 |
| `priority` | 可选优先级 |
| `status` | 未完成或已完成 |
| `reminderAt` | 可选提醒时间 |
| `createdAt` | 创建时间 |
| `updatedAt` | 最后修改时间 |
| `completedAt` | 可选完成时间 |

### 10.2 技术能力要求

- 本地数据可靠保存，退出和重启后不丢失。
- 日期、时区和跨天状态计算准确。
- 系统通知支持创建、修改和取消。
- 为未来 iPhone 版本、登录和多设备同步预留数据结构；Mac 第一版不以云同步作为前置条件。
- 关键错误可被记录，且不包含用户任务正文等敏感信息。

### 10.3 当前技术方向

- 验证阶段使用无后端的 HTML、CSS 和 JavaScript 浏览器原型，以最低成本收集交互反馈；原型代码不要求直接转换为 Swift。
- 第一版使用 Swift 与 SwiftUI 构建 Mac 原生应用，并将领域模型和业务规则组织为可供后续 iPhone 版本复用的模块。
- 第一版使用 WidgetKit 提供 Mac 桌面与通知中心小组件；后续扩展到 iPhone 主屏幕。
- 使用 App Intents 处理小组件中的完成、恢复、置顶等直接操作。
- 主应用与小组件通过 App Group 共享本地数据容器。
- 本地持久化优先评估 SwiftData；数据模型需要支持后续迁移。
- 小组件不承担通用文本输入。新增或修改正文时，通过深层链接打开主应用的极简编辑界面。
- 跨设备同步在 iPhone 版本启动时优先评估 SwiftData 与 CloudKit，不作为 Mac 第一版的阻塞项。
- AI 请求由主应用中的独立服务层处理；小组件只读取本地结果，不直接依赖实时 AI 网络请求。

### 10.4 质量底线

- 不在代码、文档或日志中保存密钥。
- 用户任务数据默认视为隐私信息。
- 数据删除、备份和导出策略需在公开测试前明确。
- 关键流程需要自动化测试，交互和视觉需要真机验证。

## 12. MVP 验收标准

### 12.1 功能验收

- 用户可以创建无日期任务，任务进入收集箱。
- 用户可以创建有日期任务，任务出现在正确日期。
- 用户可以修改任务，所有入口显示一致结果。
- 用户可以完成、恢复、延后和删除任务。
- 有时间的任务可以正常触发、修改和取消提醒。
- APP 重启后数据保持一致。
- 跨天后，昨日未完成任务能被正确识别为逾期。

### 12.2 体验验收

- 新用户无需教程即可创建并完成一个任务。
- 核心流程没有死路，每种状态都能继续下一步。
- 误操作有明确反馈，重要操作可以撤销或确认。
- 常见手机尺寸下，不出现文字遮挡、按钮难以点击或内容无法滚动。
- 深色模式若进入首版，则所有 P0 页面和系统状态都必须完整适配。

### 12.3 稳定性验收

- 不出现任务无故丢失、重复或状态回退。
- 通知权限变化后，APP 内显示与系统真实状态一致。
- 异常退出后重新打开，不破坏已保存数据。
- 已知严重问题为零，普通问题有明确记录和处理优先级。

## 13. 关键风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 功能不断增加 | 首版迟迟无法完成 | 新需求先进入候选池，不直接加入 P0 |
| 首页信息过多 | 用户仍不知道先做什么 | 以“下一步行动”作为首页唯一核心指标 |
| 日期与提醒逻辑复杂 | 发生漏提醒或错误提醒 | 先定义规则和边界用例，再实现界面 |
| 设计先于需求收敛 | 反复返工 | 先完成低保真流程，再投入高保真 |
| iPhone 与 Mac 行为不一致 | 数据或小组件操作结果难以理解 | 共用领域模型，并分别进行真机验证 |
| 小组件能力被高估 | 无法直接进行复杂文本编辑 | 小组件完成查看和轻操作，正文编辑进入极简编辑界面 |
| 过早投入正式 AI 后端 | 成本增加但核心价值不清 | 原型先模拟 AI 整理，验证需求后再接入正式模型 |

## 14. 待确认事项

以下问题会直接影响产品范围，需要在进入低保真原型前确认：

1. 第一版最低支持哪个 macOS 版本，以及只供个人使用还是计划公开发布？
2. iPhone 版本在 Mac MVP 验证到什么程度后启动？
3. 后续跨设备同步是否接受使用 iCloud？
4. 是否必须离线可用？
5. “轻记”最关键的差异点是快速记录、智能提醒，还是自动整理？
6. 小组件首版必须支持哪些直接操作：完成、恢复、置顶、延后或其他操作？
7. 首版是否需要重复任务、子任务或简单清单？
8. 是否存在已经确定的视觉风格、品牌色或参考产品？
9. 是否有明确的目标完成时间或每周可投入时间？
10. 成功的判断依据是什么：自己持续使用、完成一次公开发布，还是获得一定数量的测试用户？
